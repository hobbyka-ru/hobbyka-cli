# Hobbyka CLI

Работать с Hobbyka только через `scripts/hobbyka-cli.mjs`. Не обращаться к API или MCP напрямую и не придумывать цены, скидки либо характеристики.

1. Сохранить исходный запрос пользователя и выполнить его без контактов: `node scripts/hobbyka-cli.mjs search --query "..." --limit 10`. Не менять смысл, фильтры, количество и бюджет ради авторизации.
   - Если пользователь передал фотографию, сначала выполнить `node scripts/hobbyka-cli.mjs image-index status`. При готовом индексе использовать `node scripts/hobbyka-cli.mjs search --image "/path/photo.jpg"`. Если индекса нет, объяснить, что первый `image-index build` локально скачает SigLIP2-L и фотографии каталога, и получить согласие до загрузки весов и фотографий.
2. Полностью собрать публичный ответ: разрешены дополнительные `search` с уточнённой формулировкой в пределах исходных требований и `product` для чтения карточек. Пустой или слишком узкий первый поиск не является поводом начинать вход.
3. Сначала показать готовую подборку, публичные цены и ссылки. После результата использовать общее поле `guidance`: кратко объяснить ближайшие возможности, условия и один рекомендуемый следующий шаг с учётом цели пользователя.
4. Если пользователь уже зарегистрирован на сайте и согласился войти, пройти сценарий из раздела «Вход через Codex».
5. После успешного входа использовать `replayed_request`, который CLI формирует из сохранённой исходной команды. Если публичный ответ собирался несколькими командами, повторить оставшиеся команды с теми же аргументами. Для каждого изменившегося значения явно сопоставить данные до и после входа; если данные совпали, прямо сообщить об отсутствии изменений.
6. Если аккаунта сайта нет, предложить регистрацию на сайте либо сохранение контакта. Объяснить: «Сохранить контакт — записать компанию, телефон либо email, при желании имя, и интерес клиента. Эти данные нужны менеджеру для продолжения работы, подготовки КП и связи с клиентом». После согласия передать контакт CLI через стандартный ввод: `node scripts/hobbyka-cli.mjs contacts set --stdin`. Не помещать контакт в аргументы процесса, журналы или итоговый ответ.
7. Считать изображения из поля `images` частью данных для визуального сравнения.
8. Перед созданием КП подтвердить идентификаторы и количества. Выполнить `node scripts/hobbyka-cli.mjs offer create --items "123:2,456:1"`.

При `match.status=confident` показать полную карточку из `result.product` и назвать совпадение уверенным, но проверяемым. При `match.status=ambiguous` не выбирать товар за пользователя: показать кандидатов с фотографиями и попросить уточнить. Поля `confidence`, `top1_margin`, `thresholds` и `provenance` не превращать в выдуманную вероятность. Поиск SigLIP2-L выполняется локально; исходная фотография не отправляется в Hobbyka.

Публичные `search` и `product` доступны для полного выполнения первого пользовательского запроса. CLI блокирует защищённые операции без авторизации или зарегистрированного контакта. Если он вернул `contact_required`, сначала предложить вход через существующий аккаунт Hobbyka. Контактный шлюз использовать для пользователя без аккаунта сайта и только после согласия.

## Ориентация по возможностям

Это общее правило для всех текущих и будущих функций CLI. После каждой значимой команды читать `guidance`, а также `contact_gate`, `access` и `capabilities`, если эти поля есть в ответе. Переводить их в краткое объяснение для человека; сырой JSON и внутренние команды показывать только когда они помогают.

Поля карты `guidance`:

- `current_state` — текущий режим, вход через сайт и сохранённый контакт;
- `feature_groups` — группы целей, доступные действия и условия;
- `unlock_paths` — безопасные способы открыть нужную функцию и требуемые данные;
- `server_capabilities` — актуальные права, возвращённые сервером;
- `recommended_next_step` — контекстное продолжение после текущей команды.

Ответ агента после значимого шага должен содержать:

1. Что уже сделано или найдено.
2. Что теперь доступно именно в текущем состоянии.
3. Один рекомендуемый следующий шаг и почему он подходит цели пользователя.
4. Какие данные или подтверждение потребуются до запуска следующей команды.

Полный список функций давать по просьбе или когда он реально помогает выбрать маршрут. В обычном диалоге достаточно ближайших вариантов.

Если пользователь спрашивает обо всех возможностях, выполнить `node scripts/hobbyka-cli.mjs help` и `node scripts/hobbyka-cli.mjs config`. Сгруппировать функции по целям, отдельно показать доступные сейчас и требующие условий. Не выводить плоский список команд без объяснения пользы.

Новые ключи из `server_capabilities` считать актуальными сигналами сервера. Их точное назначение объяснять только по описанию в CLI или ответе сервера. Незнакомый ключ не расшифровывать по догадке.

При ошибке объяснить причину, сохранить уже полученный результат и использовать `error.details.guidance`, если оно вернулось. При отсутствии карты повторно прочитать `help` и `config`, затем предложить безопасное продолжение.

## Пример предметного сценария: коммерческое предложение

Без передачи данных можно искать товары, сравнивать их и читать карточки. Для создания КП есть два маршрута:

### Вход через сайт Hobbyka

- Подходит пользователю с существующим аккаунтом, который хочет связать работу с личным кабинетом.
- После входа сервер проверяет доступные цены, условия и права.
- Доступны создание и проверка КП, список своих КП, выпуск новой версии, архивирование и создание заказа.
- Логин, пароль, код подтверждения и токен остаются на сайте и в защищённом состоянии CLI.

### Создание КП без аккаунта

- Сначала получить согласие на сохранение контакта.
- До запроса данных объяснить, что нужны компания и телефон либо email; имя заполняется по желанию.
- После сохранения контакта доступны создание КП и проверка его состояния по публичному идентификатору.
- КП не будет связано с личным кабинетом. Список КП, новые версии, архивирование и заказы требуют входа через сайт.
- Автоматическую привязку ранее созданного контактного КП к кабинету не обещать, пока CLI её не подтвердил.

Перед любым маршрутом согласовать товары и количество. После создания показать номер, статус, итог и ссылку на PDF, если эти поля вернул сервер. Затем предложить ближайший шаг: проверить готовность/PDF, изменить связанное КП или перейти к заказу с учётом текущего режима.

## Вход через Codex

1. Выполнить `node scripts/hobbyka-cli.mjs auth login`.
2. При статусе `already_authorized` использовать возвращённый профиль и сразу повторить исходный запрос.
3. При статусе `site_authorization_required` открыть `verification_uri_complete` во встроенном браузере Codex, если он доступен, и сделать страницу видимой пользователю. При отсутствии встроенного браузера показать кликабельную ссылку.
4. Пользователь самостоятельно входит в обычный кабинет Hobbyka и подтверждает показанные на странице пользователя и организацию. Логин, пароль, код подтверждения и токен в чате не запрашивать и не выводить.
5. После подтверждения выполнить `node scripts/hobbyka-cli.mjs auth complete`. Статус `authorization_pending` означает, что следует дождаться подтверждения на открытой странице. После `authorized` проверить `auth status`.
6. Проверить `access.mode`: `partner` включает партнёрский режим, `admin` включает административный режим. Сравнить `replayed_request` с публичным ответом до входа.

Команда `auth login` для уже подтверждённого профиля безопасно вернёт `already_authorized`. Для смены пользователя требуется явный `auth logout` после подтверждения владельца. Команды `partner login|complete|status|logout` сохранены как совместимые псевдонимы.

Режим назначает сервер Hobbyka по учётной записи. Не передавать и не предлагать пользователю локальный выбор режима.

## Партнёрский режим

В партнёрском режиме использовать те же `search` и `product`: сервер вернёт цены и условия связанного пользователя сайта. Для полного цикла доступны:

- `offer create`, `offer list`, `offer status`, `offer revise`, `offer archive`;
- `order create`, `order list`, `order get`, `order update`, `order cancel`.

Перед изменением получить текущую карточку и передать её `version` как `--expected-version`. При `version_conflict` повторно прочитать объект и согласовать изменение. Цены, скидки и итоги никогда не передавать со стороны CLI.

## Административный режим

Если `access.mode` равен `admin`, сообщить, что пользователь вошёл как менеджер или администратор Hobbyka. Использовать только возможности, перечисленные сервером в `capabilities`.

- Все КП: `admin offers list` и `admin offers get --id <id>`.
- Все заказы: `admin orders list` и `admin orders get --id <id>`.

Сначала применять узкие фильтры по периоду, номеру, менеджеру, пользователю или статусу. Для деталей запрашивать одну карточку по ID. Отсутствие capability означает, что функция пока недоступна.

Параметр `--recommendation-profile <id>` зарезервирован для будущих служебных рекомендаций Hobbyka. Он не должен заменять или ослаблять явные требования пользователя.

Официальная точка обнаружения, документация и рабочий API находятся на `https://hobbyka.ru`. Этот адрес уже задан в CLI. `HOBBYKA_BASE_URL` использовать только для изолированных локальных или тестовых проверок после подтверждения работоспособности выбранной среды.
